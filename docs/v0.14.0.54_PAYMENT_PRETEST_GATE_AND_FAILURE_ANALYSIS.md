## Confirmed code and contract gaps identified by cross-functional review

1. **The 7/7 Preflight is insufficient to authorize Checkout.** It verifies key formats, catalog mapping, Owner shadow settings existence and webhook endpoint event names. It does not verify Owner step-up **freshness**, enabled Owner DB switch, isolated checkout intent SELECT access, the selected product's Stripe Price ID/mode, checkout rate limit, API support for Managed Payments, or server-side intent write privileges.
2. **Checkout was a one-step write path.** Following password confirmation, it would create a shadow intent and attempt Stripe session creation without an independent, consolidated read-only pre-payment audit.
3. **Stripe API contract risk:** The source sends `managed_payments[enabled]=true` without an explicit preview `Stripe-Version` header. Stripe's published Managed Payments preview changelog specifies `2026-02-25.preview` for non-SDK integrations. This release pins the checkout CREATE request version; the *actual TEST account's eligibility/TOS* cannot be proven by mere key/catalog reads. Documentation: https://stripe.kb.ryzedesk.com/articles/js/managed-payments
4. **Generic error handling hid the failing stage.** The v54 route returns allowlisted, client-safe codes for Stripe API authentication/provider feature, read-only Supabase checks, intent creation, Stripe session creation and post-creation intent binding. Provider error bodies, SQL error messages, tokens, keys and cards are NEVER displayed.
5. **Potential orphan intent/session:** Shadow intent is created before provider Checkout session. If Stripe rejects creation it can remain `prepared`. If Stripe creates a session but binding in Supabase fails, a session might exist without a bound intent. The response now explicitly says **do not retry blindly** when binding fails. Provider/ledger reconciliation and lifecycle acceptance remain required before the integration can be approved.
6. **The signed webhook secret's real pairing remains untested.** Presence/format `whsec_` is not the same as a verified HMAC delivery. Test-mode HMAC, correct account, event mapping, API version and shadow ledgers require acceptance.
7. **Token exposure:** A TEST secret and webhook signing secret were shared earlier. Both must be rotated/revoked, securely bound in Cloudflare Production and re-verified before TEST checkout. No key values in GitHub, screenshots or AI prompts.
8. **Schema compliance evidence:** Existing GU39 Supabase isolated ACL/metadata check 19/19 PASS; unrelated 22/22 scoped role revoke PASS. These are not test checkout write acceptance.

## New two-stage, release-blocking procedure

**Phase A — Source and isolated mock QA (no Stripe purchases)**
- Audit all eight selected SKU fixed expected product/price/intervals, Owner authentication + recent step-up, Cloudflare gate and Owner DB mode.
- 7/7 existing config audit and 8 additional checkout-specific guards (Owner, selected TEST product, rate limit, isolated service-only intent read, role/switch).
- Confirm TEST-only Checkout form includes exactly one item, correct price, mode and client ref, Managed Payments enabled with pinned preview API version, safe URLs and idempotency key.
- Simulate Stripe failures (unknown Managed Payments parameter, API credential denial, temporary provider issue), Supabase read/insert/PATCH failure, missing webhook endpoint, stale/expired Owner step-up, more than 12 intents per hour, eight price ID mismatches and live-mode rejection.
- Confirm **no real entitlement writes**, no live checkout and zero provider-facing POST in audit mode.
- Run unit, browser, auth, security, release and Cloudflare build checks; review signed webhook + SQL shadow apply source behavior.
- No actual Stripe TEST charge/session is permitted by this stage. Preserve all eight products, all prices, and all current production data.

**Phase B — Provider acceptance (requires Owner after Phase A and settings verification)**
1. Verify the deployed Production site shows `Payment testing interface v0.14.0.54`. Do not use Preview. Owner TEST Mode is enabled only temporarily.
2. Confirm rotated encrypted TEST API and signed TEST webhook secret, enabled webhook destination with all required eight events (no duplicated endpoint). Ensure Managed Payments account was enrolled and applicable service terms accepted.
3. Verify original 7/7 preflight, catalog 8/8, then click **Audit Checkout — No Payment** on selected SKU. It must return **8/8 PASS**. This endpoint performs *no* Stripe Checkout session POST and no Supabase writes.
4. Understand clearly: **provider Managed Payments eligibility/TOS and webhook delivery still cannot be certified read-only**. The first real TEST Checkout is the acceptance test, not an automatic production authorization. Perform it **once** only after Owner reviews remaining provider setup.
5. Verify Stripe TEST Checkout creation via Stripe dashboard; confirm `cs_test_` metadata/client reference, isolated database intent/session id, signed webhook delivery, exactly-once `evt_` ledger, isolated shadow access, and no writes to real memberships.
6. Exercise lifecycle with recorded evidence for one-time purchase, month/annual subscription, renewal, failed payment, cancel-at-end, immediate cancel, full refund, dispute and duplicate/out-of-order events. Correct all failures before approving launch.
7. Turn **OFF** Owner Test Mode and `GU39_SANDBOX_SHADOW_GATE` after acceptance. Production customer checkout and membership fulfillment remain disabled until separately reviewed.
