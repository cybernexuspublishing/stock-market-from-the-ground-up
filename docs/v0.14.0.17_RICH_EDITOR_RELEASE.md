# v0.14.0.17 — Rich Content Composer (targeted complete-file replacements)

**Release note:** This document initially covered the editor-only subset and has been updated after optional advanced interactions were added. The authoritative current package status is `v0.14.0.17_IMPLEMENTATION_STATUS.md`.

## Source baseline
Public GitHub `main` at v0.14.0.16 was inspected October 14, 2026. This is a **drop-in release containing six runtime files**, not the entire repository. The owner manually copies the four paths below into their local Git checkout; no push or deployment is performed by the assistant.

**Files:**
- `assets/js/site.js` — existing complete file plus sitewide loader for the new composer/CSS.
- `assets/js/forum-composer.js` — complete replacement of shared forum composer with safe BBCode renderer, formatting toolbar, HTML source import, emoji, preview, URL and HTTPS image insertion.
- `assets/css/rich-content-editor.css` — new responsive styling for the shared editor.
- `sw.js` — complete existing service worker with only the public cache version changed to v0.14.0.17.
- `assets/js/forum-interactions.js` — new optional discussion interaction client.
- `assets/css/forum-interactions.css` — new optional discussion interaction styles.

## User-visible capabilities
- Original member forum (new discussions, replies), Market Commons (new discussions, replies) and member self-edit dialogs.
- Owner `Site Announcements` and Owner-created individual notifications, including dynamically opened forms and inline notification editing. Announcement, Alerts, and notification-display formatting are hydrated from safe BBCode after existing application rendering.
- Toolbar: bold, italic, underline, strike, quote, code, bullet/numbered lists, alignment, whitelisted font/size/color, links, HTTPS image URLs, emoji.
- HTML source mode: paste/edit HTML and **Apply safe HTML** to convert it into BBCode. Preview shows the published formatting, without unsafe executable HTML. The underlying form submits TEXT as before. The editor alone needs no schema change; the optional interaction features require a separate additive migration after review.
- Externally hosted images are deliberately not loaded until a reader clicks **Load external image**, to avoid automatic tracking by third-party hosts.
- Standard text inputs (passwords, usernames, passwords, URLs, moderation reasons, purchase fields) are not converted to rich editor fields.

## Security safeguards
The database still stores the original text field. HTML imported through the editor is transformed by an allowlist to BBCode. The renderer escapes ordinary text, limits allowed tags to known mappings, limits fonts to a fixed list, sizes to 10–28px, colors to hex and links to http(s). Image URLs must be HTTPS. `script`, `style`, `iframe`, `object`, `embed`, `svg`, `math`, `template`, `form` and similar HTML elements are discarded; inline event handler attributes and arbitrary CSS are ignored. Editor-only files do not alter server permissions. The optional interaction SQL migration adds new restricted RPC permissions and is separately reviewed.

**Remaining security requirement**: this is a client-side output and authoring hardening. It is not a substitute for server-side sanitization if other clients or APIs are later allowed to submit true HTML. Keep downstream renderers using `.textContent` or this strict BBCode renderer—NEVER assign database text directly to `.innerHTML`.

## Limits, intentional exclusions and compatibility
- The source mode imports a **subset** of HTML (bold, italic, underline, lists, safe links, whitelisted color/font/size/alignment and image URL). It is not a general-purpose HTML/JavaScript publishing platform. Unsupported HTML is removed or reduced to text. Direct iframe/video/javascript embedding is blocked.
- No file-upload/media storage endpoint, post-icon or topic-tags schema has been added. Image URL insertion is supported; actual photo upload would require a protected storage design, scanning, quotas and moderation. We did not invent those APIs.
- BBCode is persisted in `body`. Nonparticipating external renderers and existing content elsewhere in the application may show literal BBCode tags; those surfaces need an audit before widening rich authoring beyond the listed locations.
- Do not treat an Owner annotation or lesson as a member-owned record; existing backend authorization is unchanged.
- The web editor does not introduce scriptable code widgets or arbitrary CSS. Existing forum data, drafts, announcement audience/expiration and all database privileges stay as is.

## Deployment procedure
1. Back up your working repository and ensure GitHub Desktop is clean. Check that the branch matches deployed v0.14.0.16.
2. Extract this ZIP **into the root of the same repository** preserving directory structure and overwrite the three existing JS/service worker files. Add the single new CSS file.
3. Confirm GitHub Desktop shows the exact files in `docs/FILES_TO_REPLACE.txt` (three modified and three new); no deletion of preexisting files.
4. Keep existing Cloudflare build command `bash scripts/build-pages.sh`, output `public`.
5. Commit/push yourself and verify Cloudflare preview first. Hard-refresh after success.
6. Test ordinary member create/edit/post preview and source conversion, Owner announcement save/edit/schedule/expiry, Owner-created notification send/edit/Alerts, read-only notes/automated notices, mobile layout, cross-member edit denial, and moderation queue. Review CSP/image hosting restrictions.
7. If anything fails, revert the six runtime file changes and redeploy previous source. A separately approved advanced-forum migration, if run, requires its own data-preserving rollback plan.

## Test evidence and limitations
Local Chromium smoke/XSS cases verified toolbar forms, automatic enhancement of announcement fields, BBCode rendering, safe HTML source conversion, notification display and 375px layout. JavaScript syntax checked. There was **no live Supabase Owner/member session, Cloudflare preview, or production deployment test**. Sitewide scan/mutation behavior may require regression adjustments in the actual deployed application. All owner actions must still be manually tested against the real database.
