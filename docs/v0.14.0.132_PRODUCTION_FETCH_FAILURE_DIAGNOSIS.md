## Diagnostic patch (no product behavior change)

Keep existing Worker, stable endpoint, all secrets/identity logic, daily Cron and Stripe-only detect-only reconciliation. On a rejected fetch, classify only safe known runtime categories (1042/1019, DNS/TLS, redirect or general network), without recording raw exception content, URLs, headers, token or Stripe/member data. Throw a descriptive classified error to Cloudflare Observability.

Do **not** interpret `TypeError:UNCLASSIFIED` as proof of network vs. environment. Inspect cause using authorized Cloudflare traces in that case. Do not remove authentication or permit public trigger routes.

## Required operational sequence

1. Confirm **only** `0 12 * * *` in Cloudflare's Cron list. Delete `*/1 * * * *` if present and allow propagation; don't add yet another temporary schedule. This avoids unnecessary repeated exceptions.
2. After merge and CI, update **existing** Worker from approved GitHub source using `npx.cmd --yes wrangler@4 deploy --config wrangler.jsonc` from the supplied release bundle (or `... --config workers/wrangler.billing-scheduler.jsonc` from repo root). Preserve existing `GU_BILLING_SITE_ORIGIN`, `GU_BILLING_TASK_SECRET`, `global_fetch_strictly_public` and logs.
3. Verify latest Worker deployment version changed and its Cron list remains once daily.
4. On the *next authorized* invocation, inspect **new** error classification. Do not infer diagnosis from old v131 logs.
5. Avoid infinite Cron retry loops. The Cloudflare documentation supports **local one-off scheduled invocation** without changing production triggers via Local Explorer or `wrangler dev`, but local tests may not include Production secrets or prove edge routing. Only actual production invocation verifies this integration.
6. If the classified error proves 1042, investigate same-account Pages fetch routing. If REDIRECT_REJECTED, investigate host redirects without following bearer tokens. If status is 403/503 rather than fetch rejection, investigate matched Pages secret and backend provider configuration respectively. For unknown classification, inspect tracing/subrequests with permission to view restricted logs; do not log raw credentials.
