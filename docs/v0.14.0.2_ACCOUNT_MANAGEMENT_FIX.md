## Root cause

1. Legacy Control Center grouped account functions behind several competing tabs, then hid an older account entry. The complete editor was accessible only through a secondary Edit interaction.
2. The old Users detail view was narrower than the Owner’s requested complete account editing. Several important fields and actions existed in separate API/UI paths without a direct route.
3. Existing `public.protect_profile_identity()` unconditionally rejected username changes, including explicit Owner corrections sent through the server, despite the stated exceptional-owner-correction policy.
4. Account email changes could leave `public.profiles.email` / `email_verified` behind Supabase Auth, resulting in divergent identity views.
5. Role changes could be rejected after prior identity writes. v0.14.0.2 now preflights Owner role transitions before performing Auth/Profile changes, although the overall multi-service update remains nontransactional.

## Corrected owner-facing behavior

**Always-visible navigation** (first overview group, without opening another account editor):

- Dashboard
- **Account Management** — one click opens account search, list, editor, and account actions.
- **Create Account** — one click opens the complete account creation form.
- Account Details & Support (legacy view retained for compatibility).
- Roles & Permissions, plus dedicated member management, memberships, dummy/test accounts, showcase, book/tool access, account security, activity, support, expiration, and settings are direct sidebar destinations, not hidden modal submenus.

**Edit Account** now shows all standard account areas simultaneously within one scrollable, responsive dialog:

| Area | Editable fields / Owner actions | Constraint |
|---|---|---|
| Identity | First name, last name, username, email, date of birth, account type, primary staff role | Server validates all changes. Display name is linked to username. Usernames are immutable to regular members; Owner correction requires service-side database migration. Email changes require an explicit confirmation checkbox. |
| Membership | Plan, start date, end date | Only Owner-issued manual access. Active provider-managed subscriptions cannot be overwritten. No hidden checkout activation. |
| Profile | Biography, HTTPS avatar URL, IANA time zone, locale, inactivity timeout | Existing `profiles` columns; validated on server. |
| Status | Active/watch/restricted/suspended administrative flag and reason | **Flags alone are not Auth bans**; separate explicit Auth suspension controls govern sign-in. Forum RLS still enforces its own restrictions. |
| Auth recovery | Password replacement / self-change, suspension for 24h or 7d, restore sign-in, verification and last sign-in details | Existing real password hashes are never viewable. Other Owner accounts cannot be banned through this tool. |
| Books & tools | Direct Account-specific entitlement administration; role and activity shortcuts | Uses existing Owner-only APIs; purchased entitlements are not treated as revocable manual grants. |
| Internal notes | Category, note, recent account support notes | Stored in existing private admin note table; Owner-only responses. |
| Permanent deletion | Existing audited, confirmed account deletion action | Blocked for signed-in Owner, last Owner, and known financial/subscription records. Provider privacy/retention review still required. |

Supported types remain Member, Dummy/Test, Showcase, Moderator, Administrator, and Owner. **TEST and SHOWCASE must never obtain real production membership, book, tool or staff entitlements.** Showcase viewers receive only synthetic demonstration data and have no production write path.

### Security rules and limits

- `functions/api/admin-accounts-v01353.js` authenticates a Supabase bearer token, independently reads live staff assignments, and authorizes Owner operations on the server. Frontend hiding/showing alone never grants access.
- Password retrieval remains prohibited for real members, staff, and Owner. Only separately encrypted disposable test/showcase credentials may be displayed, with short UI lifetime. A dedicated `TEST_ACCOUNT_ENCRYPTION_KEY` is recommended; do not expose keys in GitHub.
- Username edits use `supabase/migrations/v0.14.0.2_owner_account_identity_override.sql`, which permits corrections **only under trusted `service_role` JWT claims**. Test this in staging because earlier DB migrations and deployment configuration can differ. Never permit browser clients to send a service role token.
- Do not mislabel an administrative status as a true sign-in revocation. For immediate fraud/incidents use the authenticated Auth ban; application access policies must separately enforce relevant restrictions.
- Existing invoice, order, refund, provider subscription, and historical training records must not be rewritten as a side effect of account editing.
- The Account Control Center must remain usable at desktop and mobile viewport widths, including keyboard focus/scrollable navigation.

Test Create Account, identity edits, unusual names, usernames, email update consistency, DOB, role changes, last-Owner guard, manual membership dates, provider-managed billing rejection, profile preferences, flags, bans, notes, grants, deletion safeguards, lost sessions, and recovery from failed network requests.
5. Test synthetic Showcase and TEST identities cannot read/alter production records or receive production grants. Test real Moderator/Admin have no OWNER authority. Verify keyboard-only, mobile (390px) and desktop (1440px) behavior.
6. Regression-test Market Commons direct Supabase RPC/RLS write guards, reporting, moderation and anti-spam limits from v0.14.0.1; test unchanged disabled paid enrollment, book access, and Grant Web Solutions draft isolation.
7. Obtain Owner signoff on an explicit acceptance record before production release; leave checkout disabled pending its own gate.

### Known limitations / engineering follow-up

- Supabase Auth and PostgREST profile modifications cannot be committed as one ACID transaction from this Cloudflare endpoint. Failure after updating Auth may require an audited reconciliation procedure; build automated reconciliation and stronger idempotency before high-volume production use.
- Only one primary staff role is edited at a time; granular permissions remain in the existing Roles & Permissions control. This prevents accidentally overwriting independent access policies.
- Account membership changes do not modify billing-provider renewals or past receipts. Billing and entitlement reconciliation remains a separate acceptance gate.
- Staging Supabase SQL execution, live Cloudflare Pages tests, existing password-vault decryption, and actual provider-side operations were not performed in this package.
