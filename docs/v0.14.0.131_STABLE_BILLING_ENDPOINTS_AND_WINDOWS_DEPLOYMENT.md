## Owner decision — stable URLs

Public-facing URLs and private API routes referenced between services must use **stable, unversioned paths**, even though internal implementation files and SQL migrations retain version identifiers for auditability. This release removes the version from the scheduler's reconciliation endpoint and the Wrangler deployment entrypoint; it is not a blanket rename of unrelated production APIs.

- Stable private route: `POST /api/internal-billing-reconcile`, still requires the existing `GU_BILLING_TASK_SECRET` bearer token and still performs the v124 merchant/ledger reconciliation.
- Stable Worker entrypoint: `workers/billing-scheduler.js` (within existing `ground-up-billing-scheduler` Worker).
- Original `POST /api/internal-billing-reconcile-v014124` remains available as a **legacy compatibility path**; the stable endpoint directly re-exports the same handler, so there are no divergent authentication policies or duplicated writes.
- Stripe-native notifications via Stripe Dashboard remain independent of the Worker; private custom v123 outbox is preserved but **not delivered**.
- Future implementation changes should update internal module imports, not customer/API URLs or Worker service names.

## Windows PowerShell fix — no execution policy change

PowerShell may block Node's `npx.ps1` via Execution Policy. From Windows PowerShell use `npx.cmd` instead of `npx`. Do **not** disable execution policy, run `Set-ExecutionPolicy`, or run the terminal as Administrator.

From the updated extracted deployment ZIP:

```powershell
npx.cmd --yes wrangler@4 login
npx.cmd --yes wrangler@4 whoami
npx.cmd --yes wrangler@4 deploy --config wrangler.jsonc
```

The `whoami` output must identify the exact Cloudflare account containing **ground-up-billing-scheduler**. Do not paste OAuth tokens or secrets in a chat.

## Deployment order (critical)

1. Merge GitHub v131 PR after tests pass. **Wait for the main Pages project to redeploy that commit**; this introduces `/api/internal-billing-reconcile`. Do not deploy the new Worker first or it will initially call an uninstalled route.
2. In your browser, visit `https://stock-market-from-the-ground-up.pages.dev/api/internal-billing-reconcile`. The expected body is `{"ok":false,"error":"POST required"}` (405). This only proves the route exists and doesn't prove authenticated POST.
3. Confirm all temporary test Crons are removed (especially `*/1 * * * *`); the Wrangler config holds only `0 12 * * *` and overwrites previous Cron list.
4. Download/extract the v131 **standalone Worker deployment bundle**, use `npx.cmd` from PowerShell as above. Deploy only to existing `ground-up-billing-scheduler`; both `GU_BILLING_SITE_ORIGIN` and `GU_BILLING_TASK_SECRET` must remain set in Worker Production. Matching Pages Production secret is also required.
5. Verify Worker Settings includes `global_fetch_strictly_public`, daily Cron, secret bindings, and new source; Worker public route should return 404, not a billing JSON payload. No Stripe or Supabase migrations.
6. Execute a single safe scheduled test (temporary date-scoped Cron sufficiently in the future to allow propagation), verify Cloudflare Observability → Invocations and if successful review private Stripe reconciliation results. Remove test Cron afterward. Keep daily trigger until acceptable after monitoring.
7. If the private POST fails with 403, investigate secret mismatch. If 503, inspect required Pages Production configuration and provider availability. If fetch still throws, inspect Cloudflare routing and worker-to-worker restrictions using sanitized logs. Do not assume success merely because legacy public GET returned 405.

## Security and acceptance

The v124 handler is the **same imported function** under stable route, not a weaker proxy. The POST rejects missing/invalid secrets. Cron is detect-only and does not charge, grant or revoke. Any discrepancy can produce a private DB incident. Owner still must rotate the Stripe LIVE webhook signing secret exposed as text in earlier dashboard screenshot; this is independent work.

**No Supabase SQL, additional domain, email provider, cloud account, or membership pricing changes are required.**
