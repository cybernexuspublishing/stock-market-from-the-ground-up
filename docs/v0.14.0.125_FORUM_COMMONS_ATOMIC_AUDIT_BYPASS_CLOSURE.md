**Organization:** Cyber Nexus / Crown & Lantern Press  
**Project:** The Stock Market: From the Ground Up  
**Date/version:** 2026-10-20 / v0.14.0.125  
**Type:** Owner-controlled Markdown audit and migration runbook  
**Status:** GitHub source/CI development. Production Supabase acceptance outstanding.

## Material architectural/security defect

The website API already routes member changes through v116 and staff moderation
through v113, both service-only SQL transactions with mandatory audit INSERT
and rollback-on-audit-failure. **The browser-facing PostgREST table grants are
a separate authorization channel**: original v0.5 granted authenticated users
`UPDATE(title,body,ticker,updated_at)` on legacy forum topics and
`UPDATE(body,updated_at)` on replies, with RLS allowing owner edits. A member
using the Supabase browser token can bypass the v116 backend and edit those
columns without an `admin_audit_log` INSERT. Later RESTRICTIVE "member allowed"
RLS controls suspended/showcase users but does not mandate an atomic audit.
Any Commons UPDATE column grants face the same bypass class.

## Controlled fix

An additive v125 SQL transaction removes **table-level AND column-specific**
UPDATE and DELETE from authenticated, anon and PUBLIC for only the four
existing discussion-content tables. It also installs RESTRICTIVE deny policies
for authenticated direct UPDATE/DELETE so a future accidental GRANT is not
enough to reopen the bypass. Row-level **SELECT and INSERT** grants/policies,
legitimate new discussions and reports, community subscriptions, thanks,
polls, moderation-case workflow and social-feature RPCs remain unchanged.
Trusted SECURITY DEFINER create-reply helpers retain their own update access;
existing v113/v116 service-role SECURITY INVOKER RPCs remain the sole app
member/moderator edit paths and keep the required atomic audit.

**Do not REVOKE authenticated INSERT** from these tables: it would break legacy
topic/reply creation. Do not revoke service_role mutation grants. No published
forum posts or replies are changed by this migration.

## Prerequisites and production handoff (one current Supabase project)

1. Run `supabase/admin/v0.14.0.125_FORUM_DIRECT_DML_PREFLIGHT_READ_ONLY.sql`.
   If v113/v116 atomic RPCs are missing, **STOP**. Review dependencies and
   install each required owner-reviewed migration before v125.
2. Review/execute `supabase/migrations/v0.14.0.125_FORUM_COMMONS_DIRECT_DML_LOCKDOWN_OWNER_REVIEW_REQUIRED.sql`.
   The migration aborts if the service-only audit RPCs are not installed.
3. Run `supabase/admin/v0.14.0.125_FORUM_DIRECT_DML_POSTFLIGHT_READ_ONLY.sql`.
   All rows should PASS. This is structural ACL/RLS evidence, not browser proof.
4. In two real authenticated test accounts (different identities and permissions),
   verify legitimate CREATE, SELECT, member EDIT/DELETE via the Cloudflare API,
   staff hide/restore/lock/pin, and audit insert. Direct PostgREST PATCH/DELETE
   using the normal member token must fail; a different member cannot read or
   edit hidden/private content. Revoke access/suspend/showcase and repeat.
5. Race-test member edit vs moderator lock/hide: loser must receive conflict
   and the successful operation must have precisely one attributable audit row.
   An audit INSERT failure must roll back the content update. Check keyboard
   focus, announcement of 403/409 failures, error clarity and no unsafe HTML.
6. Check Forum report moderation case history against the audit ledger and
   verify that the same controls protect Market Commons and legacy content.
   Authentic market commentary is not individualized investment advice; UGC
   requires consistent moderation, disclaimers and source provenance.

## Operational boundaries

This hardening leaves the existing creator RPCs and content untouched and
requires no Stripe, product, membership or Cloudflare variable changes. After
installing SQL, refresh PostgREST schema; no feature flag is needed because
the API already uses v113/v116. Never assume a passing source check proves
v113/v116 are installed in production.

A service-role credential is fully privileged; keep it only on the server.
No arbitrary direct service-role PATCH should be introduced later. The private
audit log is the authoritative trail for controlled content edits. This phase
does **not** establish acceptability of past unlogged changes, and does not
retroactively invent audit evidence.
