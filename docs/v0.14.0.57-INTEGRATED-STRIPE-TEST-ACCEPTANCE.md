## What the unified review now checks
The existing **17 configuration checks** continue to be reported independently. The same report also shows **4 actual acceptance checks** for the Owner's most recently bound Stripe TEST intent:
1. Stripe TEST Checkout Session verified against account, intent, SKU Price, quantity, currency and amount.
2. Stripe session actually completed with `payment_status=paid`; never inferred from catalog configuration.
3. A successful server-recorded payment webhook event corroborated against the event ID returned by Stripe's TEST API. The webhook endpoint verifies the original-body signature before applying the shadow ledger.
4. Isolated Supabase shadow access record is active and the intent's current status is `test_active`.

Renewal, failed-payment, cancellation, refund and dispute evidence is separately marked `OBSERVED` only when a matching isolated event has actually been applied; otherwise `NOT_TESTED`. **No status is auto-passed by a static test or source build.** The read-only Owner GET `/api/gu39-sandbox?view=acceptance` supports programmatic acceptance checks.

## Existing safety limitations
* The GU39 acceptance suite does not grant or test production member entitlements. There is a separate Stripe v0.14.0.38 staging integration that explicitly requires a separate Supabase project. Never bypass its isolated-staging requirement.
* Real Merchant/Managed Payments authorization, true webhook delivery, live credentials, tax handling, production entitlement issuance, recurring-payment lifecycle, digital product rights and LIVE payment acceptance all remain **unverified** until suitable provider-authorized tests are actually completed.
* Production checkout remains locked. No LIVE toggle, secret rotation, automatic charge, refund, subscription, or entitlement write is performed by this release.
* A mock signed webhook CI test is engineering evidence only, not Stripe-to-Cloudflare delivery confirmation.

## Single operational acceptance sequence
Once the deployment is serving v0.14.0.57, the Owner uses the existing **Run Complete Payment Review — No Charge** once and confirms the 17/17 readiness result. The acceptance subsection will accurately show `NOT_TESTED` until a controlled purchase is deliberately started. The Owner then deliberately chooses **Open Stripe Test Checkout** for one selected existing test product, completes a Stripe TEST purchase using Stripe-published testing payment methods, and returns to the same Admin Control Center. Running **Run Complete Payment Review — No Charge** again checks the actual TEST checkout, provider payment, webhook and Supabase access evidence together. No real card, real payment or live entitlement is used.

If acceptance is `PENDING` or `EVIDENCE_UNAVAILABLE`, do **not** create another checkout; investigate the existing Stripe TEST Session, webhook event delivery attempts and isolated Supabase record before proceeding. Never use fake event inserts to claim live webhook acceptance.

**Release acceptance:** Source tests passing and deployment verified are necessary but not sufficient. One actual successful signed TEST checkout/webhook/access chain and lifecycle-specific controlled tests must be recorded before claiming those behaviors verified.
