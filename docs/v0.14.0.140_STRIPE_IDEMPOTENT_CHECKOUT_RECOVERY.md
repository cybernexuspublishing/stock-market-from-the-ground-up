## Defect found

The reviewed v58 Supabase migration **already includes** partial UNIQUE index
`gu58_one_unresolved_per_member_sku` on `gu58_live_checkout_intents(user_id,sku_kind,sku_code)`
for `status IN ('prepared','checkout_created')`. The old live customer POST inserted a
new random intent for each attempt, with Stripe's Idempotency-Key derived from that
new random value. A double-click from different tabs could have attempted two
intents. The database index (when installed) would prevent the second, but the
old API mapped the losing INSERT to generic 503; and subsequent attempts
could not reuse the original Stripe session after a network or PostgREST PATCH failure.
Stripe creating the session but the site not receiving/recording the result
left an unresolved intent indefinitely, often blocking a legitimate customer
purchase. **A new uniqueness migration is not needed unless the reviewed v58
index is absent in the actual production database.** Never blindly recreate it.

## Implemented server changes

1. Retain stable `POST /api/stripe-live-checkout` and its audited v58 handler, original
Owner TEST/LIVE mode gates, product/account and authenticated eligible-member
checks, fixed LIVE price and recurring interval verification, no books/KDP access.
2. After checking that this specific authenticated user does not already own
the paid membership/tool, read at most two service-only unresolved checkout
intents scoped by that user's verified Supabase ID **and** SKU kind/code.
3. For a matching recent `checkout_created` intent, GET the stored Stripe
Checkout Session using the configured LIVE Stripe key, validating session ID,
livemode, exact member/intent metadata, client reference, mode, USD subtotal,
unpaid/open status, expiry, HTTPS `checkout.stripe.com` host, and a separate provider GET of exactly one line item with the approved Stripe Price ID and quantity 1. Return only
the verified previously issued Checkout URL; create **no** second Session.
4. For a `prepared` record newer than **15 minutes**, reuse its immutable intent
ID, previously determined price and Stripe `Idempotency-Key` and exact same
Checkout request parameters. This permits a safe provider replay after the
initial response or database bind was lost, within Stripe's idempotency
retention window, rather than creating a new random intent.
5. The initial prepared→checkout_created database transition is a filtered compare-and-set PATCH and **must return exactly one matching bound row**; a 204 or zero-row conditional update is not accepted as durable proof. The existing signed webhook can separately recover a verified lost session binding through its service-only RPC.
6. For a competing database INSERT, the **unique index remains the authority**:
on conflict no second Stripe POST occurs; return explicit retry-later 409.
The buyer can retry to retrieve the first session after its state is saved.
7. For stale/mismatched/paid/expired/ambiguous existing intents, return an
actionable **409 (or 503 for failed provider integrity)**. **No silent deletion,
reset, free access, accidental duplicate purchase, or automatic new paid session.**
8. Continue requiring signed Stripe webhook and service-only v58 RPC for actual
entitlement fulfillment. A Checkout success redirect or this recovery path is
**never** a membership grant.

## Constraints / risks / next phase

- The 15-minute re-entry threshold is intentionally much shorter than Stripe's
typical 24-hour idempotency-key retention. Do not loosen it to auto-create a
second Session after the provider's key history could have expired.
- A stale prepared/unpaid Checkout intent **continues to block** the same SKU
until verified by an authorized operator. Future safe reclamation requires
provider evidence that the prior session is expired or a verified cancellation,
and database-atomic transition logic. Deleting an unresolved intent or manually
modifying paid entitlement records is **not** an acceptable shortcut.
- Two concurrent same-intent provider retries may temporarily return Stripe's
`idempotency_key_in_use` conflict; they must not create another session.
- The original signed webhook service-only recovery remains available even
if Checkout PATCH failed, and provider status verification is authoritative
for reuse. No webhook, Stripe product/price, checkout launch switch, billing
scheduler, book/KDP sales, education, 419 labs or 30 competencies changed.
- Independent LIVE charge validation, receipt, signed webhook processing,
member/tool entitlement, renewal/cancel/refund/dispute and Owner-approved
positive-dollar transaction remain **UNVERIFIED**. No funds authorized.
