# v0.14.0.15 — Communications & Forum Management

## Baseline, testing and deployment status
Based on `v0.14.0.14` complete source package; manually deployed source unchanged until the owner uploads this release. This candidate is **not production-verified**. User confirmed v0.14.0.7 SQL B lockdown and after-change reporting through the original forum, Market Commons and Admin reports. No more SQL B actions needed. SQL A/B are deliberately not rerun.

## Fixes and implemented workflows
1. **Site Announcements editor now appears inside the existing Admin Operations > Communications panel**, next to its read-only observations. Owner can create/edit/disable/delete and schedule start/end/duration. No longer requires finding a separate menu item installed by a later script. The existing Owner-only server controls remain authoritative.
2. **Owner-created direct member notifications** now have create, edit and delete management using the existing `user_notifications` table. The new Owner-only API denies TEST/SHOWCASE/suspended/restricted accounts and permits edits/deletion only to rows marked with notification type `owner_notice` and metadata `origin=owner_notice`. Billing, security and existing system-created messages are excluded. Member-level dismiss remains through the user-scoped endpoint.
3. **Member self-edit and soft-delete** of their own topics/replies in the original forum and Market Commons. Ownership is enforced on the server, never by frontend usernames or JS flags. Deleted content is not physically deleted and may remain available to legitimate audits. All changes use optimistic row timestamps to avoid overwriting another write. Official guides cannot be edited as normal member content.
4. **Authorized moderation** includes inspecting either forum's topic or reply by numeric ID and applying hide, restore, soft-delete, lock, unlock, pin and unpin (the latter four for topics). A 5–500 character reason is required; delete requires typed confirmation. Owner-only protection for official guides and member-deleted content. Permission checks include membership restrictions and Showcase denial. Reports queue queries both forum scopes.
5. **Admin Alert monitoring vs management**: the read-only operational notifications table remains separate from the two actual editing modules. This avoids representing metrics as CRUD controls.
6. Shared admin/forum CSS for forms and moderation; source includes an isolated regression test and browser member-controls test.

## Existing contracts used — no new write migration
`profiles` (account_kind), `admin_user_roles`, `admin_role_permissions`, `admin_user_flags`, `forum_topics`, `forum_posts`, `commons_topics`, `commons_posts`, `user_notifications`, `admin_audit_log`, `site_announcements`. All writes made through authenticated Cloudflare Functions with service-role credentials **only server-side**. New endpoints: `/api/forum-member-content`, `/api/admin-forum-actions`, `/api/admin-owner-notifications`.

Read-only preflight: `supabase/admin/v0.14.0.15_FORUM_AND_NOTICES_PREFLIGHT_READ_ONLY.sql` — use it to verify columns before controlled preview. An object present in a source migration does not prove it exists in your deployed database.

## Known limits / follow-up
- No member-post edit history/version diff table is created; admin audit records the operation and ID, not old/new body text. Full retained content history requires a reviewed migration and retention policy.
- The `commons_topics.reply_count` cached counter can require recalculation after an author soft-deletes a reply. Detail views count published rows, but index counters may not be immediately accurate until reconciliation.
- Owner-created notification recipient picker is limited to the first 200 eligible profiles. It does not bulk-message members, handle delivery via email, or schedule notification messages; announcements have start/end/duration controls.
- Moderation is a read/write dashboard, not an appeals case management system or verified enforcement of user suspensions.
- Local mocked authorization and DOM tests are not equivalent to real Supabase integration. Verify Owner notices persistence, announcement CRUD, Legacy and Commons author edits, moderations and report visibility on a Cloudflare preview branch before promotion.
- Do not enable checkout or change role grants as part of this release.

3. Preview deployment. Test an actual Owner, authorized Moderator, ordinary member, different member, restricted account and Showcase for allowed/denied mutations. Verify report visibility post SQL B.

5. If regressions arise, revert the Git commit; source-only rollback is safe for this patch because there are no schema changes. Notices or edits created while testing persist until removed through permitted workflow.
