## Root architectural issue

The existing Owner/Admin forum moderation endpoint performs **two separate independent REST requests**: a content PATCH, then an `admin_audit_log` INSERT. A network failure or permission error on the second write cannot roll back the first, and the old API explicitly returned `auditRecorded:false`. This breaks moderation accountability across both legacy forum and Market Commons topics/replies. The v105 request-size, origin and private role improvements did **not** correct this transactional defect.

## Source correction

The `functions/api/admin-forum-actions.js` service now exclusively calls `gu_v014113_moderate_with_audit` for all moderation mutations. The new database routine:

- Runs as `SECURITY INVOKER` with EXECUTE granted to **service_role only**.
- Rechecks real active Owner or `forum.moderate` staff permission, member account status, expired roles, Showcase exclusion and Owner-only Commons official guides.
- Accepts one of FOUR allowlisted private forum tables, one canonical record ID, supported moderation action, exact stale-write version and 5–500 character staff reason.
- Locks the selected row with `SELECT ... FOR UPDATE`, verifies status/version and revalidates payload limits before any mutation.
- Updates the approved content fields and writes the original `admin_audit_log` action, actor, record identifier and staff reason **within a single transaction**.
- Propagates audit INSERT failures instead of catching them: Postgres automatically **rolls back the content change as well**.
- Returns `atomic:true,auditRecorded:true` only after both writes complete; an uninstalled RPC fails closed as HTTP 503, not fallback PATCH.

The moderator inspector GET remains protected and unchanged. Member-authored forum edits, report queues, original public posts, other publications, Stripe, books, learning scores, Journal records and personal Tutor transcripts are untouched.

This is the ONLY new SQL script in this forum phase. **Owner reported successful v110 SQL** for beta workspace privileges and successful v102/v103/v105; these are different migrations and must not be repeated. This v113 SQL does not create a second database or rewrite posts. The migration is additive and may be re-executed for the same function definition, but should only be run following current owner review.

**Important compatibility gate:** Until v113 SQL is installed, staff **can still GET/inspect** moderation details but cannot make new moderation changes through the updated API. This is intentional to avoid unlogged content mutations; a missing function is a service failure, not permission to restore the old two-request path.
