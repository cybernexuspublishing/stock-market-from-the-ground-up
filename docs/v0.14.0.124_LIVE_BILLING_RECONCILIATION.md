## Defect

Webhook-only access depends on successfully receiving every signed Stripe lifecycle
event. Retries and idempotent event ledgers are necessary but not sufficient if
provider delivery is lost, payment changes while endpoints are disabled or an
out-of-order event is ignored. Do **not** grant access based on locally inferred
Stripe status or spoofed event IDs.

## Implementation

One protected service-only incremental scan cycles through currently bound
GU58 subscriptions and À-la-Carte tool passes, advancing separate ID cursors.
The backend checks the configured LIVE Stripe merchant, retrieves subscriptions
and latest invoices from Stripe, verifies signed checkout intent ID, price ID,
subscription status, currency/period evidence and local paid state. It writes
**private reconciliation alerts** on discrepancies and marks resolved issues
after a subsequent matching observation. No customer email, card number or
private Journal record is copied into these alerts.

Importantly, reconciliation **does not create/revoke access**. Only the
existing, signed GU58 webhook/fulfillment path has that authority. Payment
failures should be reported and handled through the Stripe Customer Portal;
restoring access without independently verified payment risks fraud.
A missing or stale webhook should be escalated to the owner with the original
Stripe subscription/event reviewed; never synthesize a Stripe signature.

   is not equivalent to a successful completed production sweep.

## Throughput and operational risks

Each scheduled invocation reads up to 20 plans and 20 passes. An empty batch
wraps its category cursor to zero; subsequent runs start another complete sweep.
Cloudflare Workers execution, Stripe API rate limits and real provider account
availability must be monitored. Detect-only alerts are a safety measure, not
self-healing. The current missed-renewal recovery needs a reviewed Stripe event
replay procedure before it can be considered fully automatic.

Separate Forum/Commons v113/v116 authorization/RLS/moderation checks remain
independent. Nothing in this release modifies the 419 Labs or 30 competencies.

## First subscription event recovery (real defect found in v58)

The original v58 service-only event transaction inserts/updates `site_subscriptions`/`user_tool_passes` **before** writing `stripe_subscription_id` into its checkout intent. The new v123 outbox trigger checked for an already-bound intent and therefore could miss the **first** paid activation notice. The v124 owner-reviewed SQL adds a narrowly-scoped AFTER UPDATE binding trigger on `gu58_live_checkout_intents` that queues the missing first notice as part of the same verified, service-only transaction. It verifies the exact member, SKU, session, subscription and signed-source `checkoutIntent` metadata. It uses the same deterministic notice key as v123 and cannot cause a double notice. PG16 regression exercises precisely this ordering.
