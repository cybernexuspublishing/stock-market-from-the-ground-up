# v0.14.0.78 — Unified Account Management: Scope and Control Gaps

## Owner requirement
Manage Account should be the central place to inspect and manage all account-related items, including memberships, grants, purchases, tools, books, security, roles, subscriptions and revocation actions. A membership edit must never report success if another active entitlement keeps the old access.

## Implemented in v0.14.0.78
- Read all membership grants, provider subscriptions, book rights and tool passes belonging to the selected account into the Manage Account dialog, with their statuses, sources and expiration information.
- Provide direct, individually scoped revoke controls for Owner-issued manual books and tools. Use the existing audited, Owner-only backend mutation RPC; do not delete purchase-linked evidence.
- Reject manual plan changes while active nonmanual external entitlement sources would prevent an effective change. Verify EVERY resulting membership with the canonical effective-access resolver, not only transitions to FREE.
- Preserve the pre-existing, service-only GU76 zero-dollar QA reset and replay-safe signed Stripe grant lifecycle. No additional database or Stripe product.

## Controls not yet complete — do not present these as implemented
- Paid Stripe subscriptions, refunds, disputes, period changes, cancellations and customer-support reconciliations: build provider-native lifecycle operations with signed verification, accounting/audit records and idempotent effects. Cancelling access alone does not refund a purchase.
- Role-based delegation for Administrators: current privileged account APIs authorize OWNER only. Implement explicit, independently verified ADMIN permissions while protecting OWNER role assignments, final Owner account and financial operation boundaries. Do not silently grant unrestricted OWNER powers to every ADMIN account.
- Full historical account-linked ledgers beyond each section's 100 record display: add pagination for orders, invoices, activations, credits, educational activity, support history, security changes and deletion/retention compliance.
- Multi-source transactional changes and compensation: legacy Owner mutation touches several services; when reconciliation after writes fails, the result must clearly disclose partial success rather than imply atomicity. A transactionally reviewed RPC and paid-provider orchestration are required.
- End-to-end real production testing after deploy: all entitlement sources, manual revoke, QA reset, paid subscription handling, and ADMIN/OWNER privilege denial checks.

## Operational security rule
Owner/Admin should be empowered through audited and properly authorized actions, not arbitrary deletion or alteration of payment records. Financial and historical evidence must survive cancellation and revocation. A changed plan dropdown alone is never proof that the underlying access changed.
