## Controlling Owner decision

The Owner's earlier plan was an Owner-only $0 Checkout in Admin without entitlement changes (v71). The **new controlling goal** is to verify a real **FREE member** becoming FULL_MONTHLY from the Store after a LIVE Checkout, not from the Admin console. Unlike v71, the v72 test **does change real production member entitlements** for one authorized QA account; a real signed grant is necessary for this test's acceptance. This is an explicit and limited exception to normal launch locks, **not general free monthly membership**. It must remain disabled until configured and checked.

Existing eight paid GU58 Product/Price pairs, prices, memberships, global TESTING toggle, customer LIVE checkout flags, GU58 fulfillment, signed-book commerce, digital book rights and existing production database must remain intact. The v72 test does not create a paid Stripe subscription, Managed Payments sale, PaymentIntent or future recurring billing; therefore it does **not prove real paid subscription billing**.

## Backend design / paid access safety

New endpoint: `GET/POST /api/store-zero-monthly-qa`. On GET it authenticates the member's real Supabase JWT, compares their user UUID exactly against the one allowlisted **GU72_QA_ALLOWED_USER_ID**, verifies confirmed email, checks `profiles.account_kind='member'`, obtains their *effective* plan using existing service-only `my_platform_access_for_user`, checks for an earlier v72 grant, reads the actual LIVE Product/Price/account and requires all of `GU72_ZERO_MONTHLY_QA_ENABLED=true`, `GU72_ZERO_MONTHLY_FULFILLMENT_ENABLED=true`. Without those conditions it never reveals a working checkout CTA.

Store `store.html` contains a nonpublic access-test tile in the Platform access section, hidden unless the one allowlisted FREE member passes GET. Clicking **Verify $0.00 LIVE Checkout and One-Month Access** asks for explicit confirmation and POSTs with that member's JWT. POST repeats eligibility/amount checks. Stripe creates a **payment-mode, one-time** Checkout using only the separate QA `price_`, one quantity, zero USD, disabled automatic tax, customer reference and `gu72_...` metadata. It does not send a GU58 payment-intent marker, use the eight paid prices, or enable Managed Payments. Only a Session with exact `amount_total=amount_subtotal=0`, `payment_intent=null`, `subscription=null`, correct member reference and Stripe HTTPS Checkout address can be returned. The verification endpoint never stores or collects card information. As the Stripe-hosted page is controlled by Stripe, stop without submitting it if it unexpectedly asks for card/billing details.

**Important Stripe API correction:** `payment_method_collection=if_required` is not supported for **payment**-mode Checkout (Stripe documents it for subscription mode). The Store's one-time payment-mode endpoint deliberately **does not send that field**. v71 Owner-only no-entitlement route is not used for this test and should not be used to validate member grants.

## Real signed membership-activation path

The existing permanent `/api/stripe-live-webhook` now recognises the **distinct** signed `checkout.session.completed` event tagged `gu72_zero_monthly_qa=true`. It validates Stripe HMAC, actual LIVE merchant account, provider-retrieved Session `complete`, `payment_status=no_payment_required`, one-time mode, exactly $0.00, no PaymentIntent or Subscription, allowed account identity, and exactly one line item with the separately configured free Price/quantity one. Only then does it call the **service-role-only** `gu72_signed_zero_monthly_grant(uuid,text,text,text)` function in the existing Supabase project.

**New installation file:** `supabase/migrations/v0.14.0.72_SIGNED_ZERO_MONTHLY_QA_REVIEW_REQUIRED.sql`. It adds **one SQL RPC only** (no new database/tables). It uses SECURITY DEFINER / restricted search_path / service-role-only execution, advisory lock, a single lifetime-use check per member source, existing `platform_plans`, `user_plan_grants` and `site_subscriptions`. For an eligible FREE member without active paid access or prior v72 grant, it inserts **one real** `user_plan_grants` row: `plan_code=FULL_MONTHLY`, `status=active`, `source=stripe_zero_monthly_qa_v72`, `ends_at=now()+interval '1 month'`. A duplicate/replayed or second Checkout cannot extend access. `my_platform_access` / `my_platform_access_for_user` and existing tool-access checks should then expose Full Monthly access without modifying source billing amounts. The grant **expires automatically**, never renews, and is clearly auditable. No new site_subscriptions is added because Stripe has not created a subscription.

On the Store return URL the free member sees the actual plan result after the webhook. If the event has not been applied, the page says **Waiting for signed webhook** and offers **Check membership update**. Success pages never grant entitlements on their own. A signed event that cannot reach the new service-role function remains **retryable** rather than reporting a false success.

## Acceptance and limitations

Source regression tests are mocked and include unauthorized account rejection, double-claim protection, nonzero Price/Session rejection, wrong product and bad signature fail-closed, and positive signed zero-dollar membership grant. They do not prove real LIVE webhook delivery or account entitlement operation. Do **not** label merchant-of-record acceptance, recurring subscription functionality, refunds/disputes, taxable-sale logic, or all eight paid product lifecycles PASS based on a $0 test. This QA is an authorised temporary access grant (no card charge), not a generally offered free promotional membership. A genuinely paid one-month Stripe subscription is not created.

A successful signed event and FULL_MONTHLY plan transition are the precise v72 acceptance criteria. If the Stripe event receives HTTP 503, the user should not repeat purchases; collect the event ID, HTTP response and RPC error via Cloudflare/Supabase logs and resolve before continuing. Do not rerun v65/v70 structural audits without evidence of a regression.
