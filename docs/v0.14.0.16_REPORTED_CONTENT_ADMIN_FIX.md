# v0.14.0.16 — Report-to-moderation integration and staff editorial controls

**Baseline:** complete v0.14.0.15 source ZIP, not a live production read.
**Status:** source-level candidate, mocked API and static tests passed; live Supabase and Cloudflare testing pending.
**Migration:** none. Existing status, body, title, and optimistic updated_at columns were present in the owner's read-only v0.14.0.15 preflight. That preflight does not certify policy behavior.

## Root causes
1. The main Admin panel (`assets/js/admin.js`, `loadCommunity`) retained an old report list whose only report-specific action was **Resolve**. A richer independent queue existed in `assets/js/admin-workflows.js`, but this left an inconsistent, hard-to-find workflow.
2. The richer inspector's click listener referenced `panel` without declaring it, so **Inspect** / **Review target** could fail with `ReferenceError: panel is not defined`.
3. The `admin-forum-actions` backend supported hide, restore, soft-delete, lock/unlock and pin/unpin, **but not staff editorial edits**; adding a button without a backend action would have been ineffective.

## Source changes
- Add **Inspect / Edit / Moderate** beside each report for staff with `forum.moderate`; preserve existing report **Resolve** action.
- Identify namespaced (`commons:post:N`, `legacy:topic:N`) and conventional numeric legacy targets. If target metadata is incomplete, open the inspector without asserting an incorrect target.
- Deep-link to the installed authoritative moderation panel and prefill content scope/type/ID when available.
- Fix undefined inspector panel variable and make content review show editable topic title/body or reply body, plus mandatory moderation reason.
- Extend `/api/admin-forum-actions` with authenticated permission-gated `edit`, checking status, official guide ownership, 5–500 character reason, forum-specific title/body bounds and optimistic timestamp version. Store edit indicator and reason in existing audit log; do not log private body text.
- Maintain existing hide, restore, soft-delete, lock, unlock, pin and unpin server rules; soft-delete preserves database records, not an immediate hard deletion.
- Preserve v0.14.0.7 forum reporting SQL A/B protections and service-only RPC calls; no anonymous writes or browser service key.
- Version and service-worker cache updated to avoid stale administrative assets.

## Known limitations and launch gates
- No immutable before/after revision store or transactional dual-write of content plus audit entry. The existing audit insert is best-effort after content write; **do not treat it as compliance-grade change history**. A reviewed versioned moderation RPC and append-only revisions table are needed before high-assurance staff editorial workflows.
- Staff edits to another member's words are an editorial intervention; recommended operational policy is to prefer Hide + reason for harmful content, and notify the author for material edits. This implementation does not automatically notify authors or show an edit badge.
- Moderator access is controlled by existing `forum.moderate` permission; Official Guides remain OWNER-restricted. Confirm role assignments and account flags in a preview deployment.
- Numeric, ambiguous legacy report IDs may require manual selection in the inspector; the UI does not invent a scope.
- Tests use mocked HTTP/Supabase responses; Chromium browser navigation was unavailable in the current sandbox, so there is no claim of passed browser E2E tests here.
- Do not enable paid checkout, change published books, or repeat historical SQL migrations.
