## Architectural finding

v119 checked review ownership, pre-reveal locks, source publication/rights, server cursor, and OHLCV bars through separate privileged Supabase REST calls. That creates a time-of-check/time-of-use window: an Owner can revoke a dataset between the rights check and bar read. It also magnifies partial backend failure and leaks intermediate authorization decisions into API orchestration. A single PostgreSQL function is the appropriate transaction boundary.

## Implemented

`gu_v014120_replay_review_evidence(p_actor uuid,p_review bigint)` is a service-role-only, SECURITY INVOKER RPC. It verifies review ownership, durable pre-reveal lock, explicit reveal timestamp, immutable Journal link, completed locked replay, dataset publication/licensing, and source-cursor-capped maximum 40 historical/synthetic OHLCV bars. Locks on source and session rows serialize revocation and evidence reads. SQL validates candle bounds, indices and chronology and never returns fill, P&L, future observations, or competency grades. Cloudflare checks the returned RPC contract before presenting evidence.

No new market data, user accounts, paid SKUs, mock fills, competency evidence or permission grants to authenticated/anon are added. The legacy v118 server-controlled review state machine remains the only writer for pre-reveal and post-reveal notes.

## Safe production sequence (ONE existing Supabase project)

1. Run `supabase/admin/v0.14.0.120_REPLAY_PREFLIGHT_READ_ONLY.sql` in SQL Editor. If a prerequisite is missing, do not run v120 and do not blindly reapply old migrations.
2. If the v118 lifecycle SQL is not yet installed, run the v118 dependencies and installation according to their reviewed migration runbook. The v118 installer supersedes v94/v115 for fresh installs.
3. Run only `supabase/migrations/v0.14.0.120_ATOMIC_REPLAY_REVIEW_EVIDENCE_OWNER_REVIEW_REQUIRED.sql` once prerequisites are verified. It changes one service-only function; does not rewrite past links/reviews.
4. Run `supabase/admin/v0.14.0.120_REPLAY_POSTFLIGHT_READ_ONLY.sql` and the existing `supabase/admin/v0.14.0.118_REPLAY_LIFECYCLE_POSTFLIGHT_READ_ONLY.sql`. Verify RPC grant semantics (anon=false, authenticated=false, service_role=true), enabled triggers and zero inconsistencies.
5. Perform actual **two authenticated member account** lifecycle on published rights-reviewed ORIGINAL synthetic course material or approved licensed historical dataset: start, first-bar lock, second-bar reveal, finish, check only one Journal link, due-stage 1D review, lock text, reveal bars, compare, complete, review 7D/30D later. Test second member denied, account-switch browser scrub, source revocation, mobile and screen-reader UI. Do not falsify future review due dates or invent price history in production merely to obtain a green test.
6. Once source and DB acceptance are both established, enable existing `GU_REPLAY_JOURNAL_V01494_ENABLED` in Cloudflare only with tested deployment rollback. If disabled, the backwards-compatible unlinked finish path remains available and does NOT meet complete lifecycle acceptance.

## Remaining limits

The CI PostgreSQL fixture is intentionally isolated, not your actual production data/schema. There is no verified Supabase connection with an authorized read/write tool in this session. Therefore **production database acceptance cannot truthfully be declared complete** from the repository alone.

A successful source check is not the same as a live authenticated browser lifecycle: source revocation, two-user RLS, repeat-submit races, admin disabling, accessibility, and Cloudflare binding propagation still need live verification. The 30 competencies and 419 Lab rubrics remain separately graded and owner-reviewed; completion is activity rather than proficiency. The existing Forum/Market Commons atomic moderation/member SQL v113/v116 require their own production acceptance. Do not conflate their status with replay.

## Rollback / failure semantics

If the new RPC is absent or fails, Cloudflare returns 503/409; no fallback to split REST reads occurs. Revert the Cloudflare deployment and v120 API change if necessary; do not drop existing v118 Journal tables or erase member evidence. The migration creates/replaces only the new RPC and has no data rewrite. Keep replay-to-Journal activation disabled until verified.
