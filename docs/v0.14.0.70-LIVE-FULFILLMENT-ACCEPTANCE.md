## Security defect and fix: two independent Stripe commerce flows share one merchant

The same Stripe account can receive events for **GU58 digital memberships/tools** and separately fulfilled, physically shipped **personally signed books**. The GU58 LIVE webhook subscribes to broad standard Stripe event types, so Stripe can legitimately send it a signed checkout, invoice, subscription or refund **not created by GU58**. Before v70 the GU58 code treated certain signed but unrelated events as unbound membership attempts, returning repeated HTTP 503 errors rather than routing/ignoring the unrelated commerce traffic.

The GU58 Checkout contract already applies `metadata.gu58_intent` and `metadata.gu58_member` to Checkout Sessions, and `metadata.gu58_intent` to created Subscriptions. This release ensures:

- Signed, account-authenticated Checkout Session events with **no GU58 markers** return `ignored` (HTTP 200) without consulting any member-intent table, attempting a grant, or changing book orders.
- Checkout Sessions containing **only some GU58 markers**, malformed GU58 UUIDs, or a GU58 Session whose associated Subscription lacks the expected intent marker **fail closed** (HTTP 503) rather than acknowledging a potentially paid purchase without fulfillment. They remain eligible for Stripe retry/reconciliation.
- Invoice, renewal, cancellation and subscription refund/dispute events whose retrieved Subscription has **no GU58 marker** return `ignored`; a partial or malformed marker triggers retry/error, not a payment-to-member grant.
- One-time refund/dispute events for unrelated Checkout Sessions are ignored before member ledgers are touched. A genuine GU58 refund is still bound by service-only SQL to the original payment intent, price and session.
- The existing HMAC verification, LIVE merchant ID validation, Stripe-provider GET verification, service-role RPC, transaction idempotency ledger, stale-event handling, and all independent Owner checkout switches remain unchanged.
- This patch does **not** modify the signed-book handler or move books into the eight-product membership catalog.

**Operational risk remaining:** If someone removes all GU58 metadata on a legitimately created Stripe Subscription, a subsequent standalone event can become indistinguishable from unrelated commerce. Stripe metadata integrity, signed provider replay history, first-checkout session binding and installed Supabase definition must be accepted before launch. No-source-only patch can substitute for provider-delivery acceptance.

## Managed Payments provider and tax eligibility

Stripe states that Managed Payments is a merchant-of-record solution for **eligible fully automated digital products**, subject to a separate business eligibility determination and the specific supported tax codes; account-level ordinary card acceptance does **not** prove Managed Payments eligibility. Official product eligibility: `https://docs.stripe.com/payments/managed-payments/eligibility`.

The Owner's Stripe LIVE catalog screenshots showed `txcd_10000000` (General – Electronically Supplied Services) for seven products and `txcd_20060058` (Training Services – Self-study Web-based) for Full Platform Annual. Both codes appear on Stripe's eligible-code list. **Correct tax code fit is separate from code eligibility**: the seven broadly classified products may warrant a more specific software/education code based on actual fulfillment, and this decision must be independently verified before live tax treatment is approved. Do not change an approved tax code arbitrarily. Physical/signed books, professional 1:1 advice, manual services and KDP marketplace purchases cannot be silently routed through the GU58 Managed Payments sale.

The current GU58 checkout code pins the `Stripe-Version: 2026-02-25.preview` header and includes `managed_payments[enabled]=true`. Stripe documents the feature and this preview family, but successful GET account/catalog requests **cannot demonstrate** whether this merchant is approved to create a Managed Payments Checkout Session. Do not issue a real LIVE Checkout Session to infer eligibility without separate authorized acceptance. See `https://docs.stripe.com/payments/managed-payments/set-up`.
