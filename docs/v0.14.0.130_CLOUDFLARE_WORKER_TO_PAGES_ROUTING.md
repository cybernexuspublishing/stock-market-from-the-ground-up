## Verified observations

- In the first controlled live Cron test, version `a683ec6a` executed the v129 scheduled handler but the outbound `fetch()` threw before any HTTP response; the catch block reported `Stripe reconciliation endpoint could not be reached`.
- Browser GET `https://stock-market-from-the-ground-up.pages.dev/api/internal-billing-reconcile-v014124` returned `{"ok":false,"error":"POST required"}`, confirming that the expected Pages API route exists. This does not prove an authenticated POST works.
- The same Cloudflare account serves both Worker and Pages. Cloudflare documents Worker-to-Worker fetch support through service bindings or the `global_fetch_strictly_public` compatibility flag. The observed exception is consistent with this routing problem, but the original catch concealed the underlying error code; do not claim 1042 has been proven.
- The owner tried to add `global_fetch_strictly_public` in the dashboard but the flag selector returned **No labels found**.
- At least one temporary `*/1 * * * *` test Cron trigger was observed; it ran every minute. This config replaces the full trigger list with **only `0 12 * * *`**, avoiding excess usage.

## New deployment configuration — no new Worker

`workers/wrangler.billing-scheduler.jsonc` is deliberately scoped to the existing Worker name, the unchanged v129 standalone scheduled source, and one UTC daily trigger. It enables `global_fetch_strictly_public` using Wrangler, keeps Cloudflare dashboard variables with `keep_vars: true`, keeps the existing workers.dev route enabled, and keeps logs on.

**Do not** add credentials or secret values to GitHub or the Wrangler file. The Worker uses existing `GU_BILLING_SITE_ORIGIN` (Text) and `GU_BILLING_TASK_SECRET` (Secret) managed in Cloudflare. The website's Production instance must have the matching secret.

## Owner production deployment from Windows

1. Confirm Cloudflare `Settings → Cron triggers` has no temporary every-minute trigger; if it exists, remove it promptly.
2. After the GitHub PR is merged and CI passes, download the source repository (Code → Download ZIP) and extract it, or use the stand-alone v130 deployment bundle supplied with the chat.
3. Install Node/npm if not installed (already completed in this project). Open PowerShell in the extracted repository folder (or bundle folder).
4. Authenticate Cloudflare using `npx --yes wrangler@4 login`. Complete the browser OAuth sign-in. Do not paste OAuth tokens, API keys or secrets in chat.
5. Optional account check: `npx --yes wrangler@4 whoami`. Verify it shows the Cloudflare account that contains `ground-up-billing-scheduler`.
6. From the **repository root**, run:
   ```powershell
   npx --yes wrangler@4 deploy --config workers/wrangler.billing-scheduler.jsonc
   ```
   Or, from the separately supplied **bundle directory**, run `npx --yes wrangler@4 deploy --config wrangler.jsonc`.
7. Confirm the CLI reports Worker name `ground-up-billing-scheduler` and a fresh Production version. Stop if it requests to create a *different* Worker, prompts to change another account, or reports missing bindings; investigate before confirming.
8. Cloudflare dashboard → Worker → **Settings → Compatibility flags**: verify `global_fetch_strictly_public` is now active; **Settings → Runtime variables and secrets**: verify the two variable names remain, secret encrypted, no values exposed; **Cron triggers**: verify **only** `0 12 * * *`; **Observability** remains enabled.
9. Manually test a *single* scheduled invocation using the Wrangler command `npx --yes wrangler@4 triggers` only if supported for an invoke test (do not infer this from `triggers deploy`). A short-lived dashboard test Cron at a safe future UTC time is acceptable; remove it after one execution. If using `*/1 * * * *` for diagnostics, remove within the same minute after verification and account for propagation delays.
10. Check **Observability → Invocations** for `scheduled` success, not merely zero errors. A healthy empty scan doesn't test complete Stripe lifecycle. If failure persists, collect sanitized Cloudflare event classification and examine configuration, authorization and endpoint HTTP status; do not rotate credentials without evidence.

## Rollback and production safety

- No Supabase SQL, Stripe live checkout changes, or customer access mutations are required. The Worker is **detect-only** and will record a private reconciliation discrepancy if one exists.
- `wrangler deploy` updates the named Worker in place; it does not publish the Pages application. `keep_vars` preserves existing dashboard variables, encrypted secrets are preserved by Wrangler, and `triggers.crons` sets only the approved daily schedule.
- If deployment succeeds but connectivity still fails, leave daily Cron disabled while diagnosing or roll back the Worker version in dashboard; do not restore the temporary every-minute trigger.
- Before completing billing acceptance, separately rotate the earlier screenshot-exposed Stripe LIVE webhook secret as a controlled change; it is not fixed by this Worker routing repair.
