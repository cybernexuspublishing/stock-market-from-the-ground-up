# v0.14.0.83 — Repair OWNER_REQUIRED During LIVE Checkout Activation

## Verified root cause (Owner screenshot, October 18, 2026)

The previous v0.14.0.82 direct SQL transaction failed:
`ERROR: 42501: OWNER_REQUIRED`, raised by
`public.gu_print_owner_guard_v01428()` inside
`public.gu_v01431r1_control_write_guard()`, the
`gu_v01431r1_protected_settings` BEFORE trigger on `public.site_settings`.

`commerce.checkout_enabled` is deliberately Owner/password-stepup protected.
The Supabase SQL Editor executes in privileged PostgreSQL context **without a
signed-in website member's auth.uid()/Owner JWT**. Consequently, writing that
particular protected setting from SQL Editor correctly fails. Because the old
script was enclosed in `BEGIN ... COMMIT`, **the entire attempted activation
rolled back**: Stripe route false, checkout false, testing true, 0 plan toggles.
This was a flaw in the proposed *activation path*, not evidence that the owner
configured the five Cloudflare flags incorrectly.

**Do NOT** disable the database trigger, use SQL Editor `set_config` to
impersonate the Owner JWT or relax `gu_print_owner_guard_v01428()`.
These are security boundaries protecting real customer payments.

## One-time safe repair — existing database, no extra credentials

**1.** Run ONLY the new file in the existing production **Supabase SQL Editor**:

`supabase/migrations/v0.14.0.83_AUTHENTICATED_OWNER_LIVE_ACTIVATION_REVIEW_REQUIRED.sql`

This installs a single `SECURITY DEFINER` RPC (with locked search path and
restricted EXECUTE) and does **not** enable sales by installation. It verifies
existing GU58 LIVE signed event and binding RPCs and existing eight-product
database structures. No new database, test product, Stripe charge, book change,
KDP metadata change, or historical payment mutation.

**2.** Deploy GitHub v0.14.0.83 to Cloudflare **Production** (if GitHub integration
has not deployed automatically), hard-refresh your website Admin page, open
**Commerce → Activate Paid LIVE Checkout — Eight Existing Products**. Sign in
with the OWNER account; click **Authorize LIVE Payments for Eight Products**.
The regular **Confirm Password** dialog and human verification will appear if
fresh Owner password confirmation is needed. Approve the confirmation. It is
automatically retried once by the existing Admin Supabase SDK.

**3.** The authenticated, password-verified, Owner-only RPC atomically sets:

- four positive-price `platform_plans.checkout_enabled = true`;
- verifies four existing LIVE tool SKUs remain configured;
- `gu39_sandbox_settings.enabled = false` (testing OFF);
- `gu_digital_payment_route_v01432r2 = STRIPE_MANAGED, enabled=true`;
- `site_settings['commerce.checkout_enabled'] = true` with the protected
  **Owner** trigger still active and passing normally.

This is transactionally verified and auditable. The RPC cannot be called by
anonymous users or ordinary members/Admins. It rejects missing/invalid plans,
incorrect tool prices, missing lifecycle SQL or password confirmations and
reverts every write when anything fails.

**4.** The Admin control itself then performs a **read-only** customer readiness
check against `/api/stripe-live-checkout-v01458?type=plan&code=FULL_MONTHLY`.
It only claims customer checkout ready if `liveCheckoutAvailable:true`.
Otherwise the database activation may be complete while Stripe Managed
Payments eligibility, Cloudflare redeploy or a LIVE price/webhook mismatch
remains unresolved; no payment should be made for troubleshooting.
