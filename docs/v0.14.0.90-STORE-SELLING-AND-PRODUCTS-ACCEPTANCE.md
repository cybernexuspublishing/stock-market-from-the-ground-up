## Approved V1 product architecture
- The **customer Store** has exactly three separate navigation tabs: **Memberships**, **Books**, **À-la-Carte Tools**. All ready-to-sell, authorized checkout offerings show a clear action (Choose Membership / Subscribe Now); status and prices are prominent, not buried in small badges.
- The à-la-carte tab displays **all active/public platform_tools records**, including unreleased catalog tools, and six **existing learning capabilities** not yet represented by a separately priced tool SKU: guided historical labs, skill assessments, historical replay training, learning progress, data connections, and sample interactive labs. Such capabilities are explicitly marked **Coming Soon** for independent enrollment with **Pricing to be announced**. The page link can demonstrate existing supporting educational features; it NEVER opens checkout for an unapproved standalone SKU. Once a matching code is created in Supabase, the authoritative catalog record supersedes the informational placeholder (avoids duplicates). Separate product information pages already exist for paid SKUs.
- All prices for sold tool products are sourced from live Supabase `platform_tools` and displayed in a large, high-contrast purchase block. The first-party signed `verifiedCheckout` route continues to check actual availability before a **Subscribe Now** link is rendered. Product badges, status labels, marketing copy and client-side prices cannot activate Stripe themselves.
- The existing **Admin Control Center → Products** workspace is the single management entry. Memberships, Books and À-la-Carte are separate subtabs. Existing Owner-authorized controls are reused: membership description/visibility and checkout pause; book editor with existing KDP rights/channel restrictions; tool editor with planned-product creation and safe scoped modifications. The new **Planned / Supporting Learning Offers** section shares the identical six-entry registry used by the Store, and lets authorized staff prefill **Create Planned SKU** with description, code, category and route. Saving that planned record must **not** activate checkout, create a Stripe Price, or confer access.

## Price, fulfillment, compliance boundaries
- **Existing positive-price LIVE Stripe Prices cannot safely be edited like normal text.** The backend explicitly refuses price changes on LIVE tools, LIVE tool status activation and changes to premium entitlement flags. Stripe Price is typically an immutable price object; changing an existing offer's price requires creating/mapping a new price, handling existing subscribers, legal billing notices, and confirming signed webhook fulfillment. A product being listed or showing a price alone does not constitute such approval. This project does not alter the provider or membership entitlement authority.
- For **books**, the Store displays available customer purchasing formats only when existing website and retailer conditions allow them. Where no verified retailer/direct route exists, display Coming Soon and avoid invented dollar prices. Book learning focus is now **“What you’ll learn in this book”**, and the previously approved Foundations Book I covers stock/exchange meaning, market participants/bids/asks/orders and risk awareness; this project does not rewrite any manuscript or KDP metadata.
- All six planned-supporting capabilities are **not necessarily independent paid products**. Calling them Coming Soon means enrollment/standalone pricing are pending a deliberate Owner SKU and development decision, not a promise of a future paid plan.
- All changes in this PR are customer UI, shared roadmap registry, safe planned SKU prefill and regression tests. No database migration, service secrets, new subscription price, new paid customer charge, unauthorized access grant, book edit or KDP update.
- Existing paid catalog and print/ebook availability stay under their current authorized systems. Do not mark paid fulfillment verified without a real signed positive-dollar transaction and member grant.
