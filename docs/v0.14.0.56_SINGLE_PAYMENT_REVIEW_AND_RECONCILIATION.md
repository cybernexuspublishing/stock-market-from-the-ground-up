## Owner's instruction: one combined workflow

No more separate repeat rounds of verification steps. The Admin Control Center → Payments & Billing → Stripe Payment Testing now provides one prominent **Run Complete Payment Review — No Charge** button. It consolidates the old 7 configuration checks, 9 independent checkout guards, an actual provider read of all 8 TEST products/prices, a scan of Stripe Checkout sessions for previously unbound isolated TEST attempts, and the independent LIVE launch lock into one response. Old tools remain available under a collapsed **Advanced diagnostics** section.

### What the combined review does (read-only)

1. Verifies the current Stripe TEST account, encrypted TEST credentials' formats, authorized webhook URL and all 8 subscribed event types. A `whsec_` string alone cannot certify valid HMAC delivery.
2. Queries all 8 existing TEST products/Prices; checks amounts, recurrence, active status and correct test account. Does not recreate catalog items or alter tax settings.
3. Verifies Owner role, password step-up, Cloudflare TEST gate, Supabase Owner mode switch, selected SKU/Price, server-side shadow SELECT and anti-repeat limit.
4. Scans **all unbound `prepared` intents for the signed-in Owner**. Removes the earlier dangerous 24-hour time window: unresolved intents do not silently become authorized once they age out.
5. Cross-checks each prior intent with Stripe's paginated TEST Checkout Sessions list, using `created[gte]` and `created[lte]` around the original test attempt, matching exact `client_reference_id` AND metadata for a verified candidate, with expected Price ID, subtotal, quantity, currency and `livemode=false`. Listing is limited to 10 pages per intent: partial pagination, ambiguous results, unexpected account, unknown price, Stripe read failures or >25 unresolved intents **block resolution**.
6. Reports two distinct states: **TESTING** stops new live checkout creation through server-side mode gates; **LIVE selected** does NOT permit real charges until the separate Owner production-launch flag and provider approval are complete.
7. Creates zero Stripe Checkout sessions, refunds, subscriptions, shadow ledger entries or real user entitlements while *reviewing*. No secret value is sent to browser.

The integrated report is the normal operator path. The existing LIVE/TESTING slider remains separate and must be used deliberately; the review never flips it.

### Owner's reported earlier failed attempt

The existing production Supabase report provided by Owner:

```
status: prepared
attempts: 1
without_stripe_session_id: 1
with_stripe_session_id: 0
created_at: 2026-10-18 00:39:34.300576+00
```

The lack of a Supabase `session_id` does NOT establish Stripe never created a session. The combined review interrogates Stripe's TEST Session listing before allowing any isolated ledger reconciliation.

**Resolution is never silently automatic.** If and only if the authenticated Owner has exactly one unbound attempt and the provider scan is unambiguous and exhaustive, the Admin report provides **Resolve Existing TEST Attempt — No Charge**. This is an explicit Owner-confirmed, recent-password-protected follow-up to the single review, not a new checkout or customer purchase:

- `NO_MATCH_FOUND`: after the record is older than the 30-minute matching interval plus a 5-minute safety margin and a complete scan confirms zero matches in the request window, change precisely that record from `prepared` to `test_failed`. Matching conditions include Owner identity, original ID, status=prepared, `session_id IS NULL`. This is a bounded provider observation rather than absolute proof about every possible event; the Owner must review the result.
- `MATCHED_VERIFIED_SESSION`: if exactly one valid Stripe TEST session matches the original intent ID, metadata, Price ID, amount and currency, bind only its `cs_test_` identifier and change status to `checkout_created`. If an earlier provider webhook arrived prematurely, subsequent signed event acceptance/replay still requires verification.
- `MATCHED_SESSION_NEEDS_REVIEW`, `AMBIGUOUS_MULTIPLE_SESSIONS`, `STRIPE_SCAN_INCOMPLETE`, `STRIPE_SCAN_UNAVAILABLE`, invalid timestamps, more than one unbound intent, or any other inconsistent condition: **STOP**. No provider mutation or blind retry.
- The targeted Supabase update must affect exactly one row; zero or multiple rows are rejected. A reconciliation attempt records an Owner admin audit entry, with an explicit warning if separate audit logging fails.
- This operates exclusively on **GU39 shadow records**, never on real subscription/entitlement/order tables.

### LIVE mode and launch: one release review, not three repetitive projects

The v0.14.0.55 LIVE/TESTING slide switch is retained. Source tests and one integrated readiness panel cover both. However no static code or one-click inspection can certify actual Stripe **LIVE merchant eligibility**, the live account's product/Price mappings, live webhook secret/delivery, signed fulfillment/refund behavior, shipping/physical goods rules or active existing subscription state. Such verification requires provider credentials and an Owner-authorized controlled external transaction during final acceptance. Live checkout remains OFF by default; the switch alone cannot activate it.

**Stripe Managed Payments eligibility and applicable terms** are separately unverified by GET catalog inspections; do not claim the website is live-ready because 17 source/connection checks pass. No tax decisions are reopened.
