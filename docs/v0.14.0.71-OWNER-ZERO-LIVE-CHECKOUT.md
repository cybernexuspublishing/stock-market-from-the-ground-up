## Architecture / controls

The new stable route `/api/owner-zero-live-checkout` offers an Owner role/password-step-up protected read-only GET configuration check and **separate, deliberate POST** to create a $0 one-time LIVE Stripe-hosted Checkout Session. The Admin Payments & Billing UI adds **Owner LIVE $0.00 Checkout — Separate QA Product (No Membership Grant)**; it is not a public storefront listing. There are no additional Supabase tables, no member/entitlement writes and **no new SKU** in the eight-entry `GU58_STRIPE_LIVE_CATALOG_JSON`.

The POST is blocked by default with `GU71_ZERO_LIVE_QA_ENABLED` absent/false. The Owner may enable it **only for an explicitly approved verification window**. All Cloudflare LIVE checkout / GU58 fulfillment flags and TESTING mode are unchanged. The API strictly checks: matching authenticated LIVE merchant account, Product active/LIVE with metadata `gu71_zero_qa=true`, Price active/LIVE and bound to that Product, `unit_amount=0`, USD, one-time, fixed per-unit, no quantity transform, not in any GU58 paid product, Owner role + recent password confirmation, exact same-origin POST and explicit action confirmation. The only created Stripe object is a **Checkout Session** under the Owner's click. The session must report amount_subtotal=0 and amount_total=0, payment_method_collection=if_required, no payment intent, no subscription and a trusted Stripe HTTPS hosted URL, or the link is **not returned**. There is no managed-payments parameter or recurring product setup. Owner QA metadata uses `gu71_...` only, NEVER `gu58_...`.

The existing version-independent LIVE webhook `/api/stripe-live-webhook` now recognizes only the distinct `checkout.session.completed` QA event bearing GU71 metadata. It authenticates the signed Stripe HMAC with the existing LIVE `whsec_`, checks LIVE merchant account, retrieves the actual completed $0 Checkout and verifies the single exact QA Price, zero line-item amount, Owner correlation and absence of any GU58 metadata. A genuine QA event returns HTTP 200 body `qa-zero-signed-verified-no-grant`, **even while GU58 paid member fulfillment is OFF**. An altered or nonzero QA payment is rejected, not acknowledged. All other events retain their pre-existing signed GU58 approval/fulfillment gates. No Supabase billing or entitlements are touched by QA.

The Admin return URL contains a Stripe Checkout session ID. The **Owner-only** GET independently retrieves that session from Stripe and reports amount_total=0, completed status, no payment intent/subscription, and no entitlement. An HTTP 200 QA delivery in Stripe Workbench establishes that the LIVE signing secret and webhook destination can verify this one free event, **not** that the paid GU58 activation/renewal/refund/dispute logic functions correctly.

## Scope limits / consumer / fee considerations

Stripe supports free Prices with `unit_amount=0`; see https://docs.stripe.com/api/prices/create . Checkout Sessions can be payment-mode/one-time and report `no_payment_required`; see https://docs.stripe.com/api/checkout/sessions/object . This **does not charge a card** if the $0 safeguards and Stripe-hosted free checkout operate as specified, but is still a LIVE Stripe action that creates a Session and event records, and Stripe may have account-specific service charges unrelated to customer card debits. The test does not certify $69.99/$699/$2,499 paid charge execution, recurring invoice success/failure, Managed Payments availability or actual customer entitlements. Complete separate provider and Owner acceptance before enabling LIVE paid sales.
