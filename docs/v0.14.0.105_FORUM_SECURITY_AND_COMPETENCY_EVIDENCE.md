## Batch A — Forum/Commons privacy and secure write boundaries

Existing production forum has **two** posting surfaces (legacy forum and Market Commons), separate moderation, editing and reporting APIs. These must not be conflated merely because their IDs happen to match.

- Shared `forum-request-guards-v014105.js` applies same-origin mutation checks and 16–23 KB server-side *actual byte* limits, including chunked requests without a Content-Length header; malformed JSON fails with explicit non-500 client status. This protects authorized edits, moderator actions and content reports.
- Member-edit API denies editing a locked topic itself (not just replies to a locked topic), including read-for-edit. Editing still compares real author ID, current published state and optimistic `updated_at` version against a server-only Supabase read.
- Moderation GET now selects only fields needed for the editing interface; a generic `SELECT *` could reveal other private row columns. Post lookups deliberately exclude topic-only columns. Public moderation errors cannot reflect raw database error text/schema internals.
- Post/edit/report flows keep their existing distinct Supabase schemas, staff roles, account restrictions, Owner editorial guides, audit and quote UI. No new forum product, price, private database or role is invented.
- Isolated tests cover unauthorized and cross-origin writes, locked topics, byte-length, invalid JSON, moderation projections, modern service API keys and the historical forum regression suite.

**Important remaining forum architectural risk:** Existing moderation/member edits perform a content PATCH followed by a separate audit INSERT. If audit fails, the system currently reports `auditRecorded:false` but **cannot roll back the mutation**. A future version must consolidate moderation and audit into one database transaction/RPC and verify direct member forum creation against the currently installed RLS. Browser-origin checks are defense-in-depth and do not replace bearer-token or Postgres RLS authorization. Provider-backed AI may be used in the forum later only if members are explicitly entitled and content moderation/retention/provider safeguards are separately approved.

## Batch B — Correctly connect server-graded Lab performance with the 30 official competencies

**Problem found:** `lab_training_attempts_v014` records privately graded conceptual exercises, but `competency_evidence` can remain empty. Yet simple completion or a mechanical arithmetic answer cannot justify 4-dimensional mastery. This must be solved without manufacturing skill certification.

**Implementation:**

- The existing 419-Lab canonical mapping generates 419 one-skill **candidate** records. Even when editorial metadata offers up to three subject associations, this new grading bridge uses only the first candidate. ALL 419 begin `candidate`; **zero are auto-approved**. Each maps to one of the existing approved competency definitions; no 31st is created.
- `training-editor.html` / `assets/js/training-editor.js` now display the primary candidate and all available official competency codes, with a separate explicit Owner approval button ONLY for an exact previously independently reviewed rubric version.
- New server-only `GET .../training-editor?action=knowledge-map` and `POST ...?action=approve-map`. Server rechecks Owner status, expired roles, restricted/suspended profiles and optional staff MFA. The private SQL approval RPC verifies the exact reviewed rubric version, active competency, authoritative Owner role and appends an audit entry in the **same transaction**.
- New optional private `gu_v014105_sync_reviewed_knowledge(p_actor,p_attempt)` uses a completed, server-graded `lab_training_attempts_v014` score. ONLY after the mapping is approved for the exact rubric version, it writes **one `knowledge` dimension**, source_type `quiz`, by idempotent insert into the existing `competency_evidence` table. It never invents recognition, decision, process, unseen market observations, trading profit or mastery.
- The interactive grading endpoint automatically tries this sync on successful completion, and preserves the original grade if the optional bridge is missing or unapproved. Existing attempted grades can later be reconciled from the member Skills page using `POST /api/interactive-training?action=sync-reviewed-knowledge`. SQL caps each reconciliation to 500 eligible assessed attempts per call.
- `competencies.js` now uses **Conceptual Evidence Only** rather than `Developing` or `Proficient` when attempts lack the independently assessed four dimensions. This is a correction in truthful learning claims, not a downgrade of authentic student scores.
- An Owner cannot quietly assign prior knowledge evidence to a different competency after the record exists: SQL denies reclassification without a separate reviewed data correction.

It adds one new private mapping table with 419 unapproved suggestions and three service-only RPCs; uses the **existing Supabase project**. It has NOT been installed by a GitHub merge. ## Acceptance controls

**Security:** Test restricted/Showcase/expired Owner roles; legacy and Commons authors; malformed/chunked requests; topic lock changes while editing; private staff notes and database errors; role expiry and MFA; public read denial of mapping/keys; direct-membership RLS and CSP. Tests do not replace live database inspection.

**Curriculum:** Individually review each question, keyed answer, tolerance, failure explanation, which specific competency is tested, and whether its cited evidence is merely hypothetical. A missing reviewed mapping remains candidate and awards NO evidence. Competency mastery still requires four distinct dimensions, validated independent assessments, and original requirements for minimum count/unseen passing streak. `original_synthetic` bars remain fictional.

**Operations:** Sitewide payment/membership fulfillment, real model costs, journal and simulator data integrity, market history licensing, accessibility, privacy/data retention, and financial-advice disclaimers remain separate acceptance gates.
