## What v134 implements

- Stable unversioned read-only GET `/api/billing-reconciliation-health` within existing Cloudflare Pages Functions.
- Server requires Supabase member session, exact OWNER role and active password reconfirmation before any service-key private-table reads.
- Fetches the existing plan/tool cursor activity timestamps; counts existing GU58 signed-source recurring membership/tool records and open/resolved reconciliation issues, with counts by issue classification. Only bounded `HEAD` count requests and two-row cursor reads; never exposes user IDs, Stripe IDs, provider responses or credentials.
- A new accessible `LIVE Billing Reconciliation — Private Evidence` panel in the **existing Admin Control Center → Commerce / Payments & Billing** view; requires Owner navigation permissions and manual button click. Backend role check is authoritative.
- Clear distinction between recent cursor activity, unresolved discrepancy evidence, a completely empty signed-source recurring ledger, and unverified full-sweep/paid-checkout/webhook acceptance. Non-atomic concurrent count changes are explicitly labeled.
- Read-only, `no-store`/noindex JSON. No new database migrations, manual SQL, Stripe API calls, charges, launch approvals, paid entitlement writes, or notification delivery.

## Production checklist — only necessary Owner actions

1. Merge GitHub PR after relevant security/functional CI passes. Let **existing** Cloudflare Pages production project deploy the merged commit; do not redeploy or change the currently working scheduler for this feature.
2. In Cloudflare Worker settings confirm only the approved permanent daily `0 12 * * *` schedule is active. Historical logs from `*/1 * * * *` do not prove it remains enabled.
3. Sign into website Admin as OWNER, complete normal password reconfirmation, navigate to Commerce / Payments & Billing. Under **LIVE Billing Reconciliation — Private Evidence**, select **Review Billing Reconciliation — No Charge**.
4. Inspect actual per-category signed-source record counts, cursor activity and unresolved issues. Zero subscriptions means no recurring paid ledger records were observed; it is **not** a passing paid integration test. Stale cursor activity or unresolved alerts require investigation. If v124 tables are missing, use the existing v124 **read-only preflight**; do not blindly rerun migrations.
5. Separately perform the previously approved v81 single read-only eight-SKU database acceptance (if current output is not already recorded). Positive-dollar LIVE paid billing, cancellation, renewal, refund and signed webhook access are still **Owner-controlled** and require explicit charge consent, Stripe account/price verification, and observed member access. A successful scheduler does not authorize any charges.
6. Retain private response evidence without sharing tokens, customer IDs or service secrets. If the Owner reports red status, examine only the safe report classifications and evidence for corrective work. Do not enable all eight customer checkout gates to obtain test data.

## Security and acceptance

**Source tests:** must verify unauthenticated requests, non-Owner and missing password step-up cannot read billing data; service-key reads are exclusively GET/HEAD; malformed/missing v124 state refuses false success; API cannot mutate Stripe, subscription entitlements, database or Owner launch flags. Browser uses `textContent` for reported data and has accessible headings/captions.

**Known limitation:** Multiple PostgREST exact-count HEAD calls are not one atomic DB transaction. If a scheduled reconciliation changes issues during review, the two totals may temporarily disagree; this is reported, not silently treated as failure of Stripe. Full-sweep evidence requires repeated observations or further instrumented server-side acceptance. Paid lifetime purchases do not produce recurring subscription rows and are separately covered by the v81 eight-SKU signed fulfillment audit. No customer-facing launch approval is derived from this panel.

**Rollback:** Revert only the v134 Pages source/assets if necessary. Do not roll back the working scheduled Worker or v124 database state. No new database objects must be deleted.
