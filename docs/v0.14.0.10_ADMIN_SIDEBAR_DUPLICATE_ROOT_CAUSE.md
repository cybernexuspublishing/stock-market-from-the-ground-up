# v0.14.0.10 — Admin Sidebar: Repeated Controls Root-Cause Repair

## Incident evidence

The Owner's screenshots show dozens of repeated **Competency Cases**, **Feature Inventory**, and **Lab Registry** entries under Books & Learning on the deployed Admin sidebar after v0.14.0.9.

## Reproduced root cause

`admin-navigation.js` in v0.14.0.9 flattened **all button nodes** from legacy module groups and executed `nav.replaceChildren(fragment)`, deleting those modules' original group mount nodes.

`assets/js/admin-operations.js` uses `ROOT_ID='v135-unified-operations'` as its mounted guard, and observes direct child mutations under `#admin-tabs`. Once its guard disappeared, its mount watchdog created a new group with the six actions, then `admin-navigation.js` moved the action buttons and deleted the marker again. This feedback loop produced the repeated entries captured in the screenshots. Merely deactivating older group-reorganization scripts did not prevent the interaction.

## Implemented remediation

1. One canonical navigation owner remains; older sidebar group builders remain retired.
2. The *original* module wrapper nodes survive in the inert `#cc-preserved-module-roots` container inside `#admin-tabs`. This keeps their mount markers connected, and leaves their operational panels intact.
3. Original live action buttons and click handlers are moved into the canonical visible groups; buttons are not cloned.
4. Stable action keys (IDs, `data-*` action keys, and internal link URLs) deduplicate repeated injections. This also deduplicates Manager inventory.
5. Native module permission checks and Owner-managed visibility still apply. Hiding a menu item is not an authorization change.
6. CSS hides only empty original mount group shells, never the real visible action nodes.
7. A browser regression test simulates a module watchdog checking its original wrapper every 55 ms and proves there is a single mounted module and one instance of each action after repeated regrouping. Additional duplicate injection is removed while the retained action's original click handler works.

## Local verification vs production

Local Chromium and repository tests do not certify actual Supabase, Owner, live CSS, or Cloudflare deployment state. A production acceptance test must: (a) wait >30 seconds with Admin open; (b) verify no repeated entries; (c) open Accounts, Learning Operations, Lab Registry, Feature Inventory, Reports and Control Registry; (d) check sidebar controls remain consistent after reload; (e) verify the release badge and service-worker update.
