## 2. Material defect A — Cloudflare treats failed email delivery as a successful run

The existing private email endpoint returns **HTTP 207** for partial notification delivery and marks its JSON `ok:false,failed:N`. HTTP `207` is a 2xx status, so a Worker checking only `Response.ok` incorrectly reports a successful run despite a failed delivery. The scheduled Worker now validates both endpoint HTTP status and structured JSON: success requires no failed email attempts, no reconciliation errors, and no subscription discrepancies. A 207, malformed body, mismatched response or failed dependency rejects the scheduled job with a privacy-safe error. Both endpoints are still invoked independently within a single invocation.

Cloudflare Workers monitoring must be configured by the owner to surface failed Cron invocations; throwing an error alone does not configure alert delivery.

## 3. Material defect B — exhausted leased notices stranded forever

Installed v123 `gu_v014123_claim_notices` could select a `leased` row after its lease expired, but when `attempts>=12`, an additional UPDATE filter prevented any state change. That row remained `leased` and invisible to normal operational review forever. The new **additive v128 function correction** replaces only the existing claim function (same signature and role scope), and transitions any expired/due exhausted row to `dead`. It does not return such rows for sending. An already-active lease is left alone until expiry; a legitimate unexhausted row remains eligible for a bounded claim and its existing idempotent email provider send. Previously stranded, already-expired/due exhausted rows are marked `dead` once during installation.

**Important:** Dead-letter status is not proof of undelivered email. The provider might have accepted a prior message before acknowledgement failed. Review the provider delivery record and outbox ID privately before any replay; do not mass-reset attempts or delete dedup keys.
