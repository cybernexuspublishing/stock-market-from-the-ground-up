# v0.14.0.7 — Legacy Forum Report Consolidation and Database Permission Closure

**Status: source-tested engineering candidate; not production-deployed.** Baseline: Owner-supplied v0.14.0.6 ZIP. **Owner applies SQL and deploys files manually.** Checkout remains disabled.

## Confirmed production inspection inputs

Owner supplied read-only database output: all 13 inspected tables, 12 specified columns, six named RPCs exist and have RLS enabled. `forum_reports` had member INSERT privilege, overlapping permissive INSERT policies, and a restrictive production-member insert policy. `public.user_has_tool_access(uuid,text)` initially allowed inherited PUBLIC EXECUTE, and the Owner manually revoked that permission, reporting the verified results `anon=false`, `authenticated=false`, `service_role=true`. No assumption is made about unrelated tables or permissions not inspected.

## Defect addressed

- `/forum-topic.html` previously inserted directly into `public.forum_reports` using the browser's Supabase client; that bypassed the newer atomic daily-limit and duplicate-check RPC.
- The new UI uses accessible reason/details fields, member Bearer token, and the existing server endpoint `/api/commons-report` rather than direct SQL insertion.
- Unlike Market Commons, the old forum uses `forum_topics` and `forum_posts`. Their numeric IDs can overlap. The server now requires a `scope:'legacy'`, a verified topic ID, member-scoped legacy read RPCs, and a legacy-namespaced content ID. Market Commons reporting remains `scope:'commons'` by default.
- The atomic SQL report RPC now permits *only* `commons:<topic|post>:<id>` or `legacy:<topic|post>:<id>` matching the declared type, with the same per-member 24-hour limit, duplicate prevention, advisory transaction lock, allowed reasons and review record. It rejects restricted, suspended, nonproduction and active SHOWCASE roles in addition to the API checks.
- The legacy forum read-gate SQL guard is upgraded to reject restricted as well as suspended accounts.
- All existing report rows are preserved. The reporting route and historical API filenames remain stable.
- SQL phase B revokes member direct INSERT and drops only the **three named insert policies verified in the supplied database report**. It does not delete read-own report policies or report rows.
- The previously confirmed `user_has_tool_access` grant correction is included idempotently for clean installations; the Owner already applied it in the current project.

3. Verify the moderator can see and resolve the `legacy:*` and `commons:*` reports without leaking a user's identity.
4. **Deploy the frontend/API update to production** only after preview acceptance. Cloudflare build remains `bash scripts/build-pages.sh`, output `public`. Ensure old service-worker/browser caches have updated by testing a hard refresh. Keep paid checkout OFF.
5. **SQL phase B — AFTER verifying the new frontend is live:** Run `supabase/migrations/v0.14.0.7_B_FINALIZE_FORUM_REPORT_LOCKDOWN.sql`. It revokes direct member INSERT and removes the redundant insert policies, while retaining SELECT policies and historical reports.
6. Verify final SQL returns `anon_insert=false`, `authenticated_insert=false`, `anon_rpc=false`, `authenticated_rpc=false`, `service_rpc=true`, and entitlement EXECUTE remains `anon=false`, `authenticated=false`. **Important:** A and B are **new write migrations**, not read-only inspections. Run once each in order. If the website fails between A and B, the old reporter interface remains temporarily functional because direct INSERT has not yet been revoked; do not apply B until the deployed new report interface passes validation. If A fails, don't deploy the matching frontend/API update until fixed. If B fails, it rolls back, leaving Phase A's temporary legacy capability. Neither script enables payment processing.

No historical Labs, authored grading answer keys, payments, client-site publishing, or production data have been changed.
